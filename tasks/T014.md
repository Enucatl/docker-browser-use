# T014 — Jev action space + Browser Use ↔ Jev adapter

## Goal

Define the constrained Jev action space and an adapter that maps Browser Use observations/candidates into Jev inputs and maps Jev outputs back to Browser Use actions.

## Context

Ideal loop: observe → Jev chooses one action → execute → observe. Large LLMs are not the default decision maker.

Initial action space:

- `CLICK`
- `TYPE_TEXT`
- `SCROLL`
- `GO_BACK`
- `NAVIGATE`
- `DONE`
- Reserved specialized actions (stubs OK): `BITWARDEN_LOGIN`, `BITWARDEN_IDENTITY`, `BITWARDEN_CARD`

Jev receives: goal, browser state summary, candidate elements, available operations. Retain confidence/probabilities for debugging and approvals.

## Dependencies

- T001 (package exists). May stub Browser Use types if T013 not merged yet — prefer real types if available.

## In scope

1. Formal action schema (Pydantic models or equivalent) including targets and parameters.
2. Adapter interface:
   - `to_jev_request(observation, goal, history_summary) -> JevRequest`
   - `from_jev_response(resp) -> AgentAction`
3. Pluggable Jev client interface with a **fake/deterministic** implementation for tests.
4. Document how element indices/selectors are referenced safely.
5. Unit tests for mapping edge cases (empty candidates, DONE, low confidence).

## Out of scope

- Full control loop (T015)
- Real Jev production credentials beyond config hooks
- Bitwarden execution (T027)
- Text LLM (T016)

## Acceptance criteria

- [ ] Action space documented and encoded once
- [ ] Fake Jev client drives deterministic unit tests
- [ ] Adapter never requires raw passwords in the request object
- [ ] Probabilities/confidence preserved on the decision object for audit

## Suggested files

```text
src/<package>/policy/actions.py
src/<package>/policy/jev_adapter.py
src/<package>/policy/jev_client.py
tests/test_jev_adapter.py
```

## Implementation notes for the model

- Keep the action space deliberately small; resist adding clever actions early.
- If Jev’s real API is unclear in-repo, isolate it behind the client interface and record assumed request/response shapes in the module docstring for easy swap.
